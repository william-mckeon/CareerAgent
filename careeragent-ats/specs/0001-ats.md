# 0001 — careeragent-ats: the deterministic keyword-coverage scorer

> A new microservice that scores a resume against a job description by keyword
> coverage — a fast, explainable, **model-free** signal for the coach. One small,
> **pure** box: no database, no model calls, no network egress, no file parsing.
> Port **8010**. Phase 7 (#16, artifact generation — the light half).

## Goal

The coach (`careeragent-api`) wants to answer *"how well does this resume line up
with this posting, and what is it missing?"* That is a deterministic text problem
— extract the posting's important keywords and check which ones the resume
contains. It should not cost a model call or a database round-trip, and every
decision should be explainable to the user.

So it is isolated into a tiny box: `{resume_text, job_description}` in, a coverage
report out. It holds nothing and reaches nothing.

```
careeragent-api ──POST /ats-score {resume_text, job_description}──▶ careeragent-ats
                ◀── {score, coverage, matched, missing} ──────────
```

## The spine

```
POST /ats-score {resume_text, job_description}
  → if job_description blank/whitespace → 400  (never a fake 0/0)
  → keywords = extract_keywords(job_description)
      tokenize (tech-punctuation-preserving)
      detect known multi-word tech phrases
      collect unigrams; drop stopwords + hiring fluff + pure numbers
      overlap-dedupe; salience-rank; cap at 40
  → for each keyword: matched if it appears in resume_text
      exact word-boundary  OR  alias-group member  OR  guarded rapidfuzz ≥ 88
  → score = round(100 * matched / total)   (0 if total == 0)
  → {score, coverage:"m/t", matched:[...], missing:[...]}
```

## Contract

**`POST /ats-score`** (`X-API-Key: ATS_API_KEY`) → `AtsResponse`
`{score:int(0-100), coverage:str, matched:[str], missing:[str]}`.
Body `{resume_text, job_description}`.
- `400` — empty/whitespace `job_description` (`"job_description is required to
  score against."`).
- empty `resume_text` is allowed → score `0`, all keywords missing.
- `503` — `ATS_API_KEY` unset. `401` — bad/missing `X-API-Key`.

**`GET /health`** → `{status, service}` (no auth).

## Keyword extraction (`src/ats.py::extract_keywords`)

1. **Tokenize** with a regex that preserves internal/trailing tech punctuation:
   `c++`, `c#`, `node.js`, `ci/cd`, `.net`, `asp.net`, `k8s`, `3d` each stay one
   token. Everything is lowercased.
2. **Known multi-word phrases** — a curated set (`machine learning`, `deep
   learning`, `rest api`, `data science`, `distributed systems`, `ci/cd` [single
   token], `amazon web services`, …) is detected as contiguous token runs, longest
   first, and emitted as single keywords.
3. **Unigrams** — every remaining token, minus:
   - **stopwords** (articles, prepositions, conjunctions, pronouns, aux verbs);
   - **hiring fluff** (`team`, `player`, `fast-paced`, `responsibilities`,
     `requirements`, `experience`, `years`, `ability`, `strong`, `excellent`,
     `work`, `join`, `looking`, `etc`, `communication`, `skills`, …);
   - **pure numbers** and bare single characters.
4. **Overlap dedupe** — if a multi-word phrase is kept, its constituent unigrams
   are dropped *unless* a constituent is independently salient (known-tech or a
   role noun), so `machine learning` doesn't triple-count as `machine` +
   `learning` + `machine learning`.
5. **Salience rank + cap** — score each candidate: known-tech +100, known-phrase
   +90, tech-punctuation +55, multi-word +45, role-noun +30, capitalized-in-JD
   +20, plus frequency and length tie-breakers. Sort descending (stable on
   first-seen order) and keep the top **40**. This bounds the denominator so a
   sprawling posting can't dilute the score, and prefers real skills over prose.

## Keyword matching (`src/ats.py::keyword_matches`)

A keyword is **matched** if any of these holds, checked cheapest/strictest first:

1. **Exact word-boundary match** (case-insensitive). Boundaries are defined as
   *"not flanked by an alphanumeric"* (`(?<![a-z0-9])…(?![a-z0-9])`) rather than
   `\b`, so tech punctuation works AND short tokens stay precise:
   - `java` does **not** match `javascript` (next char `s` is alphanumeric);
   - `go` does **not** match `google`.
2. **Alias group** — a small hardcoded map of equivalents whose spellings differ
   entirely: `postgresql`↔`postgres`, `kubernetes`↔`k8s`, `aws`↔`amazon web
   services`, `.net`↔`dotnet`, `ci/cd`↔`cicd`, `c#`↔`csharp`, `golang`↔`go`, …
   The resume matches if it contains any group member (exact word-boundary).
3. **Guarded fuzzy near-match** — `rapidfuzz.fuzz.ratio(keyword, token) ≥ 88`
   against each resume token, attempted **only** for keywords ≥ 4 chars. This
   catches minor spelling variants (`PostgreSQL`/`Postgres` also via alias,
   `Kubernetes`/`Kubernets`). `fuzz.ratio` (symmetric edit similarity) is used —
   **not** `partial_ratio`, which would score a substring like `java` inside
   `javascript` at 100. Short tokens (`go`, `js`, `ml`, `c#`) are matched exactly
   only; their real variants live in the alias map.

## Behaviour rules
1. **Never fabricate a `0/0`.** An empty/whitespace JD is a `400`, not a fake
   perfect-or-zero score.
2. **An empty resume is valid** → score `0`, everything missing.
3. **Deterministic + explainable.** Same inputs → same output; every `matched`/
   `missing` decision is a rule, not a model guess.
4. **Precision over recall on short tokens.** Better to miss a fuzzy `go` variant
   than to falsely credit `google`.

## Residual limits (honest)
- **This is not a real ATS.** No proprietary ATS ruleset, no per-keyword
  weighting, no semantic or seniority understanding. It is a transparent coverage
  heuristic — a gap-finder, not a hiring verdict.
- **Keyword-stuffable.** A resume can inflate its score by listing terms it can't
  back up. The score measures *coverage*, not competence.
- **Heuristic extraction.** A rare skill phrased unusually, or an unlisted
  acronym, may be mis-extracted or mis-matched. The curated vocab + alias map are
  easy to extend.
- **English-oriented.** The stopword/fluff/tech lists are English.

## Non-goals
- Fetching the JD or parsing resume files (that's `careeragent-fetch`; text
  arrives already extracted).
- Storing anything (the coach owns any persistence, via `careeragent-dossier`).
- Any model call, embedding, or semantic similarity — matching is deterministic
  and lexical by design.
- Rewriting the resume or generating bullet points (a heavier, model-backed job).

## Design decisions
- **Separate service, not in the api agent** — keeps a self-contained, cache-free,
  independently testable scorer out of the coach, and lets it be reused by any
  future surface (e.g. a batch "score against N postings").
- **No model** — coverage is a lexical problem; a deterministic scorer is faster,
  free, reproducible, and explainable, which matters for user trust.
- **rapidfuzz only** — the one analysis dependency; its C++ core ships manylinux
  wheels, so the image needs no apt layer and no build toolchain.
- **`fuzz.ratio`, length-guarded** — deliberately conservative to protect the
  `java`/`javascript` and `go`/`google` cases from false credit.
