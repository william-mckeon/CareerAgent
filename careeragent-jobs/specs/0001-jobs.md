# 0001 — careeragent-jobs

> The **background/async job runner** for CareerAgent (P7 #18a — the "do not poll" half).
> `careeragent-api` enqueues a SLOW task here and returns immediately; a worker runs it off the
> request path and **injects the result into the conversation** when done. It is a new service —
> it changes **no existing service's code**.

---

## Goal

Some capabilities are too slow to run inside a chat turn — a repo-review fan-out over the user's
GitHub can take minutes. Running it inline blocks the turn (or times out); making the user poll a
status endpoint is a poor experience. `careeragent-jobs` fixes exactly that gap: `careeragent-api`
**enqueues** the work and gets an id back instantly, a **worker** claims and runs it, and the
finished result is **injected as an assistant message** into the job's conversation via
`careeragent-sessions` — so it simply appears, no polling.

There is **no agent loop and no model** in this service. The worker calls leaf services directly
(this slice: `careeragent-review`). A scheduler/cron for recurring jobs is a **later slice** and is
explicitly out of scope here.

## Concepts

- **job** — a `{kind, spec, conversation_id}` unit of work under a stable `id` (UUID), with a
  lifecycle `pending → running → done | failed` and an `attempts` counter.
- **kind** — the job type. The registry (`src/jobtypes.py`) maps a kind to an async handler. This
  slice ships one: `review_repos`.
- **spec** — opaque per-kind parameters the handler interprets (e.g. `{repos, limit, focus, force}`).
- **worker** — a single in-process asyncio task (started in the FastAPI lifespan) that claims one
  pending job at a time, runs its handler, stores the result, and injects it into the conversation.
- **injection** — on success the worker POSTs the summary to `careeragent-sessions`
  `/conversations/{id}/inject` so it lands in the transcript as an assistant message.

## Where it sits

```
careeragent-api ──POST /jobs──▶ careeragent-jobs (:8011) ──┬─▶ careeragent-review  (:8007)  the work
                                (worker, own Postgres)      └─▶ careeragent-sessions (:8005)  inject result
```

`careeragent-api` calls `POST /jobs` and returns the id to the chat turn; the turn ends. Minutes
later the worker finishes and the result appears in the conversation.

## Contract (HTTP) — `X-API-Key` except `/health`

### `POST /jobs` — enqueue
Body: `{ "kind": "review_repos", "spec": { ... }, "conversation_id": "<uuid|null>" }`
- `201` → `{ "id": "<uuid>", "status": "pending" }`.
- Unknown kind → `400` `{ "detail": "unknown job kind '<k>'" }`. (`review_repos` is the only valid
  kind in this slice.)
- Malformed `conversation_id` → `400`. Missing/invalid key → `401`. Store down → `503`.

### `GET /jobs/{id}` — status/result
`{ id, kind, status, attempts, result, error, conversation_id, created_at, updated_at }` | `404`.
(`spec` is worker-internal and never exposed.)

### `GET /jobs?conversation_id=<uuid>&status=<s>&limit=<n>` — list
Array of the same fields, **newest first**. None-valued filters are dropped; `limit` is capped at 100.

### `GET /health` — no auth
`{ "status": "ok"|"degraded", "service": "careeragent-jobs", "database": "ok"|"unreachable" }`.
`status` is `ok` when the database is reachable.

## Store (own Postgres, schema `careeragent_jobs`)

```
jobs(
  id              uuid pk default gen_random_uuid(),
  kind            text not null,
  spec            jsonb not null default '{}',
  conversation_id uuid,
  status          text not null default 'pending',   -- pending|running|done|failed
  attempts        integer not null default 0,
  result          text,
  error           text,
  created_at      timestamptz not null default now(),
  updated_at      timestamptz not null default now()
)
index jobs_claimable        on jobs (created_at) where status = 'pending'
index jobs_by_conversation  on jobs (conversation_id, created_at desc)
```
Everything is schema-qualified to `careeragent_jobs` (never bare `public`), so sharing one Postgres
instance later is a config-only switch (point `JOBS_DB_HOST/NAME` at it). `init.sql` creates it on a
fresh volume; `store.ensure_schema()` creates it idempotently at startup for an existing volume.

**Claim is atomic and concurrency-safe:**
```sql
UPDATE jobs SET status='running', attempts=attempts+1, updated_at=now()
WHERE id = (SELECT id FROM jobs WHERE status='pending'
            ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED)
RETURNING *;
```
`FOR UPDATE SKIP LOCKED` lets multiple workers (or replicas) claim disjoint jobs without blocking or
double-running one.

## Worker behavior

1. `claim_one()`; if empty, sleep `JOBS_WORKER_POLL_SECONDS` (interruptible) and poll again.
2. Dispatch on `kind`; `await handler(spec, deps)` → a summary **string**.
3. Success → `finish(id, 'done', result=summary)`, then (if `conversation_id`) inject the summary.
4. Handler exception → `retry_or_fail(id, str(exc), JOBS_MAX_ATTEMPTS)`: re-queue while
   `attempts < max`, else mark `failed`. With the default cap 3 a job runs at attempts 1, 2, 3.
5. **One bad job never crashes the loop** — every iteration is wrapped; errors are logged and the
   loop continues. Injection is best-effort (the job is already `done`).

## Auth (compartmentalized, house pattern)

- **Inbound** `X-API-Key` = `JOBS_API_KEY` (careeragent-api ↔ jobs). Constant-time compare, read at
  call time; `/health` is unauthenticated.
- **Outbound**: `REVIEW_API_KEY` to `careeragent-review`, `SESSIONS_API_KEY` to
  `careeragent-sessions`. Separate boundary keys — never reuse the inbound one.

## Acceptance

- [ ] `POST /jobs` with `review_repos` → `201 {id, status:"pending"}` and a row is enqueued.
- [ ] Unknown kind → `400` with the documented detail.
- [ ] The worker claims a pending job atomically (`pending → running`, `attempts+1`), runs it, and
      on success stores the result and injects it into the conversation.
- [ ] A handler failure re-queues up to `JOBS_MAX_ATTEMPTS`, then marks the job `failed`.
- [ ] `GET /jobs/{id}` / `GET /jobs` return the documented shapes; unknown id → `404`.
- [ ] Missing/invalid `X-API-Key` → `401`; `GET /health` (no auth) → `200`.
- [ ] `init.sql` creates everything in schema `careeragent_jobs`; repointing `JOBS_DB_HOST/NAME`
      needs no code change.
- [ ] Existing services are unchanged.

## Non-goals (this spec)

- **A scheduler / cron** for recurring jobs (weekly role scan, etc.) — a later slice (#18b).
- **More job kinds** — only `review_repos` here; the registry makes adding kinds a local change.
- **Multi-worker scale-out tuning** — the claim is already `SKIP LOCKED`-safe, but this slice runs a
  single in-process worker.
- **A push channel to the frontend** — delivery is via `sessions` injection (the transcript is the
  system of record); live push is the frontend's concern.

## Design Decisions

- **A dedicated service, not a thread in `api`.** Slow work needs its own process lifecycle,
  restarts, and (eventually) horizontal scale, without holding a request worker or coupling to the
  gateway's memory.
- **Deliver via `sessions` injection, not a status the client polls.** The transcript is the system
  of record; injecting the result puts it exactly where the user is already looking. "Do not poll."
- **`FOR UPDATE SKIP LOCKED` from day one.** Even though this slice runs one worker, the safe claim
  costs nothing and makes adding workers/replicas a config change, not a rewrite.
- **Own DB now, shared later.** Schema-qualified + env-driven connection → a config-only switch to a
  shared Postgres instance.
